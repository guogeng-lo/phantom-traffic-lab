# check_wiki.py：Git歷史掃描改用完整檔案判斷SHA-256表頭

- **類別**：檢查程式修正（不是Graph的節點）
- **日期**：2026-11-11
- **改的檔案**：`scripts/check_wiki.py`、`tests/test_check_wiki.py`
- **標準有沒有改**：有，而且**是看到誤判之後才改的**。使用者批准（第3輪後的決定第5點），範圍限定在「掃Git歷史時，SHA-256表頭怎麼判斷」。哪些字串算雜湊值、排除只用在學號和手機，這兩條都沒動。

## 問題

上次的雜湊值排除（`runs/2026-11-11-check-wiki-hash-exclusion.md`）在掃Git歷史時，只看diff前後3行的上下文來找表頭。

4462639在審查包的SHA-256表格中間加了幾列，那段diff從第58行開始，表頭在第48行左右，看不到。結果同一個雜湊值又被報成學號。

修改前的`--strict`（`runs/logs/2026-11-11-history-fullfile-strict-before.log`）：

```
[錯誤] Git歷史 4462639 pipeline/review/n3-package-r3.md：疑似像學號的9位數字

文獻 6 篇（算進5篇的獨立論文 6 篇），證據卡 39 張（pending 0 張）。
錯誤 1 個，警告 0 個。
exit=1
```

## 怎麼改

- 還是只掃每個commit**新增**的行。
- 新增的行裡有反引號包起來的64位十六進位時，用`git show <commit>:<檔案>`讀那個commit裡的**完整檔案**，從頭追表頭，判斷那一行是不是在SHA-256欄。
- 讀不到完整檔案就不排除。
- 順便修了一個原本就有的漏洞：以前用「`+++ `開頭」判斷檔名，如果新增的內容剛好以`++ `開頭，會被當成檔名而漏掃。現在用`@@`標頭寫的行數判斷哪些行是內容。

## 流程同時改的

使用者決定：正式流程改成**commit之後、push之前**跑完整的`check_wiki.py --strict`，直接看結束代碼決定能不能push，不能用`tail`只看最後一行。
