# 建立和審查證據卡檢查程式（2026-11-11）

這份不是Graph 8個節點的執行紀錄，是在正式ingest之前，先把第2關要用的檢查程式`scripts/check_wiki.py`做出來、測過、再審一次的紀錄。

## 第一次建立（commit ff89515之前）

做法：寫好`check_wiki.py`，再寫`tests/test_check_wiki.py`，用26個情境故意弄壞資料，看它擋不擋得住。

**第1次跑：1個失敗**

```
[FAIL] 主張裡只有年份，units寫無數值
    預期：沒有錯誤
    實際：[錯誤] wiki/cards/demo2000-claim.md：主張裡有數字，units 不能寫「無數值」（要寫單位或「無因次」）
```

原因：程式要先把主張裡的年份拿掉再找數字，用的是`\b`分隔，但Python把中文字也當成「字」，所以「2000年」中間沒有分界，年份沒被拿掉。改成「前後不是數字」的寫法。這是檢查程式的錯。

**第2次跑：測試本身壞掉**

```
AssertionError: 測試寫錯了：demo2000-claim.md 裡找不到 'related: '
```

原因：測試資料裡`related: `後面的空格在存檔時被去掉了，測試找不到要改的字。改成找`related:`。這是測試寫錯，不是檢查程式的錯。

**第3次跑：1個失敗**

```
[FAIL] 檔案裡有本機路徑
    預期：錯誤裡有「本機路徑」
    實際：沒有錯誤
```

原因：Windows使用者資料夾路徑的樣式多跳脫了一層反斜線，實際上要找的是兩個反斜線，所以永遠找不到。這是檢查程式的錯，如果沒有這個測試，之後在Windows上留下本機路徑也不會被擋。

**第4次跑：26個情境，失敗0個。**之後commit ff89515。

## 重新審查（斷線恢復後）

先確認沒有東西遺失：GitHub上的main和本機都是ff89515，29個檔案都在。從GitHub重新拿一份乾淨的repo重跑，`check_wiki.py`錯誤0，26個情境全過，選題階段的`test_ovm.py`和`page3_check.py`輸出跟原本的log逐字相同。

接著對照`AGENTS.md`和`pipeline/requirements.md`，逐條看規則有沒有真的被程式檢查，找到這些「規則有寫、程式沒擋」的地方：

| 問題 | 規則出處 |
|---|---|
| 只掃現在的檔案，沒掃Git歷史 | AGENTS第11節、需求「公開前掃整個repo和Git歷史」 |
| 沒掃手機號碼 | AGENTS第0節第6條寫了電話 |
| 索引裡指向已經不存在的檔案不會被發現 | AGENTS第2節「所有文獻和證據卡都要列在索引」 |
| 一篇論文沒有任何confirmed證據卡也會算進5篇 | 需求「實際讀取並整理」 |
| 主張有數字，locator寫「全文」也會過 | AGENTS第4節「數字要到頁碼、章節、公式或圖表編號」 |
| 欄位重複時後面的直接蓋掉前面的 | — |
| 學號樣式會把log裡的小數（例如1.412345678）誤判成學號 | — |
| 自己的模擬可以指向不會上傳的檔案，別人沒辦法核對 | 需求「別人不用拿到本機檔案也能追溯」 |
| AGENTS第9節說`test_ovm.py`要在audition/裡執行，但指令是從repo根目錄跑的 | — |

修改：
- `check_wiki.py`補上上面每一項。Git歷史的問題平常只列警告，加`--strict`才算錯誤，因為歷史要改只能改寫歷史，要先問使用者；push前一律跑`--strict`。
- 每一項都加了測試，總共37個情境。
- AGENTS第9、11節改成新的指令和push前的規則。

**新的測試真的有在測嗎**：把新的37個情境拿去跑修改前的`check_wiki.py`（ff89515版本），結果：

```
[FAIL] 檔案裡有手機號碼
[FAIL] log裡的小數不能誤判成學號或電話
[FAIL] 欄位重複
[FAIL] 索引列了不存在的卡
[FAIL] 有數字的主張，locator只寫全文
[FAIL] 自己的模擬指向不會上傳的檔案
[FAIL] 歷史裡有金鑰：平常是警告
[FAIL] 歷史裡有金鑰：--strict是錯誤
[FAIL] 歷史裡有PDF：--strict是錯誤
[FAIL] 有confirmed卡的論文才算進5篇
[FAIL] 沒有confirmed卡的論文不算
共37個情境，失敗11個。
```

新加的11個在舊版全部失敗，原本的26個還是通過；換回新版是37個情境，失敗0個。「log裡的小數」那項在舊版失敗，代表舊版真的會誤判。
